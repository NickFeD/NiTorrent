## 2. Зафиксированное направление

| Часть | Ответственность |
| --- | --- |
| Torrents | Коллекция, пользовательские намерения, подготовка, передача, удаление, повтор ошибок, метаданные, хранение торрентов и настройки движка |
| Desktop | Окна, навигация, экраны и их локальное состояние, трей, режимы и диалоги закрытия, тема, обработка активаций Windows |
| Updates | Проверка обновлений и сценарий обновления; первоначально допустима небольшая отдельная папка |
| App | Точка входа, сборка зависимостей, выбор реализации движка, запуск и согласованное завершение |

Логическая структура Torrents: Contracts, Domain, Application, Persistence, Engines. Это зоны ответственности, а не требование создать отдельный проект для каждой папки.

- Contracts: команды, однократные запросы, наблюдение текущих данных, сведения о доступных возможностях.
- Domain: модель и правила коллекции, пользовательские намерения.
- Application: сценарии, сессия, восстановление, координация наблюдения.
- Persistence: каталог и источники, переносимые пользовательские настройки.
- Engines: внутренние интерфейсы и конкретные адаптеры; специфические настройки и внутреннее состояние каждого движка.

Один активный движок на приложение; изменение выбора вступает в силу после перезапуска. Одновременное распределение торрентов между движками не требуется. Конкретный второй движок в найденных документах не выбран.

### Объём первого этапа — подтверждён владельцем

- Перестройка архитектуры, механизм подписок и архитектурный контроль с текущим MonoTorrent, с сохранением существующих возможностей.
- Одно главное окно с существующими страницами. Новые окна и расширенные экраны в этап не входят; архитектура должна позволять их добавить позднее.
- Второй рабочий движок и новый сценарий обновления не входят в этап. Для будущих движков требуется сравнение возможностей, а не немедленная интеграция.
- При скрытии в трей страницы освобождают подписки на данные для отображения. У трея остаётся собственная подписка на необходимые ему данные. После возвращения окна активная страница заново подписывается и получает актуальное состояние; невидимые страницы не подписываются автоматически.
- Созданный трей владеет своей подпиской до освобождения трея/остановки приложения. Создание и освобождение не должны дублировать подписки.
- Обычная минимизация в панель задач и поведение неактивных вкладок не были явно уточнены: на первом этапе сохраняется действующее поведение вне явно согласованного скрытия в трей.
- При потере связи остаются последние данные с отметкой «связь потеряна»; наблюдение восстанавливается автоматически. Это не разрешение автоматически повторять команды или бесконечно перезапускать движок; действующая политика ошибок движка сохраняется.
- Скорость и прогресс обновляются ориентировочно раз в секунду. Пользовательская настройка частоты отложена. Это целевой темп актуализации UI при доступном источнике, а не гарантия получения ответа от сервера за секунду и не обязательная частота событий самого движка.
- Неподдерживаемые сведения/действия показываются недоступными с объяснением, а не скрываются и не подменяются нулевыми значениями.

## 3. Актуальные данные и подписки

Требования владельца:

- Нужны текущие значения: скорость, прогресс, сведения о соединениях и другие данные для отображения. История не требуется в рамках этого перехода.
- Потребитель явно открывает и закрывает наблюдение выбранных данных. Однократный запрос не должен скрыто запускать бессрочное наблюдение.
- Дополнительный сбор для отображения включается по потребности и прекращается при отсутствии потребителей этих данных.
- Отсутствие подписчиков не останавливает скачивание, раздачу, восстановление и применение команд. Работа, необходимая самому ядру, продолжается.
- Разные движки могут получать данные разными способами; UI не должен знать способ получения.

Предлагаемая семантика интерфейса — требует окончательной фиксации в ТЗ:

- Подписка определяется видом данных и областью: всё приложение, коллекция либо конкретный TorrentId.
- Новый подписчик получает последнее доступное состояние и дальнейшие обновления; ожидание первых данных и недоступность обозначаются явно.
- Два окна с одной потребностью используют общий сбор. Закрытие одного не отключает наблюдение другого.
- После освобождения последней подписки прекращаются дополнительный опрос, обработчики и подготовка данных для неё; собственный сбор движка может продолжаться.
- Медленный потребитель текущих показателей не блокирует остальных и не создаёт неограниченный буфер. Допустима замена устаревших снимков последним; служебные ошибки и результаты команд этим правилом не отбрасываются.
- Для больших списков возможны полные снимки или изменения, но новый подписчик и восстановившийся потребитель должны получать согласованное актуальное состояние. Конкретный формат не выбран.
- Подписки освобождаются при закрытии экрана и при остановке приложения. Согласованные правила скрытия в трей приведены в разделе 2; правила иных состояний видимости не следует домысливать.
- Ошибки источника, отсутствие поддержки и реальные нулевые значения различаются. Последнее известное состояние при потере связи явно помечается, автоматическое восстановление наблюдения возвращает показ актуальных данных.

SSE упоминался владельцем как аналогия доставки обновлений. Сетевой протокол между локальными модулями не требуется. Адаптер серверного движка использует поддерживаемый сервером способ, включая опрос, если потока нет.

## 4. Предлагаемые правила зависимостей

Это проект правил для согласования и последующего автоматического контроля:

| Потребитель | Допустимые зависимости |
| --- | --- |
| Desktop | Собственная реализация, Torrents.Contracts, публичный интерфейс Updates, UI-библиотеки |
| Torrents.Contracts | Собственные переносимые модели и согласованный минимальный набор общих библиотек; без типов реализации, движка, WinUI и хранения |
| Torrents.Domain | Собственная предметная модель; без Desktop, App, движков, хранения и host |
| Torrents.Application | Contracts, Domain, внутренние абстракции; без конкретного движка, Desktop и App |
| Persistence и адаптеры движков | Необходимые внутренние интерфейсы/модели Torrents и свои внешние библиотеки; без Desktop/App |
| Updates | Собственная логика и согласованные абстракции окружения; без реализации Desktop/Torrents |
| App | Публичные точки регистрации и lifecycle модулей; без пользовательской логики и прямого управления менеджерами движка |

Дополнительные правила:

- Межмодульные обращения идут через явные интерфейсы. Реализации скрываются через `internal`, где возможно.
- Типы MonoTorrent и будущих движков не выходят в Desktop и внешний интерфейс Torrents, включая свойства, события, generic-аргументы и возвращаемые типы.
- Desktop не получает репозиторий для обхода команд и не редактирует живую модель коллекции.
- UI-диспетчеризация принадлежит Desktop; ядро не захватывает dispatcher или время жизни окна.
- Сессия, движок и координация сбора общие на процесс; состояние выбора, фильтров и навигации принадлежит окну.
- Циклы зависимостей модулей запрещены. Общая папка/сборка не используется для обхода правил.
- Настройки разделяются по владельцам. Страница настроек в Desktop не делает Desktop владельцем настроек движка.
- Физические ссылки App для регистрации допускаются только в месте сборки зависимостей. Сам факт такой ссылки не разрешает остальному коду App вызывать реализацию модуля.

## 5. Защита архитектуры

Владелец предложил архитектурные unit-тесты или более удобный способ. Рекомендация: совместить ограничения компиляции и архитектурные тесты, затем дополнить их проверками поведения.

### 5.1. Ограничения компиляции

- Выделить публичные контракты и реализации в проекты там, где это даёт реальный запрет нежелательного доступа. Не создавать проект для каждой подпапки автоматически.
- Использовать `internal` и небольшой публичный интерфейс, включая явные точки регистрации.
- Зафиксировать разрешённый граф ProjectReference и допустимые места PackageReference. Учитывать транзитивные ссылки: отсутствие прямого ProjectReference само по себе не гарантирует изоляцию.
- Число проектов, размещение WinUI/XAML и точки регистрации выбрать после проверки текущих ограничений сборки.

### 5.2. Архитектурные тесты

Реализован отдельный набор `NiTorrent.Architecture.Tests`, запускаемый в CI и локально, без запуска окон и сетевого движка. Для полного анализа он собирает Windows-приложение, затем читает метаданные сборок без загрузки WinUI в процесс тестов.

Рассматривались [NetArchTest](https://github.com/BenMorris/NetArchTest) и [ArchUnitNET от TNG](https://github.com/TNG/ArchUnitNET). Для текущего набора правил выбраны стандартные `System.Reflection.Metadata` / `PEReader` и чтение XML проектов: проверяются зависимости сборок и ссылки на типы MonoTorrent, не загружая Windows-сборки в CLR. Дополнительная библиотека не требуется. Проверки дополнены созданием контрольных IL-сборок с запрещёнными зависимостями и проверкой циклов. Это не анализ всех транзитивных вызовов методов; допустимая область зависимости App от Infrastructure ограничена единственным типом регистрации.

| ID | Проверяемое правило |
| --- | --- |
| ARCH-01 | Граф ссылок проектов соответствует разрешённым направлениям и не содержит циклов |
| ARCH-02 | Domain/Application/Contracts не зависят от UI и конкретных адаптеров |
| ARCH-03 | Desktop использует Torrents через Contracts; не обращается к репозиторию, сессии реализации и типам движка |
| ARCH-04 | Публичные контракты не раскрывают типы реализации, изменяемую живую модель и типы внешнего движка |
| ARCH-05 | Пакет MonoTorrent и альтернативные SDK используются только в разрешённых адаптерах; такие типы не встречаются вне адаптеров |
| ARCH-06 | Updates не зависит от реализации Torrents/Desktop; модули не зависят от App |
| ARCH-07 | Обращения App к реализациям ограничены разрешённым местом регистрации и lifecycle-интерфейсами |
| ARCH-08 | Каждый обязательный модуль и его типы реально попали в анализ; пустой набор не считается успешной проверкой |

Для проверки самих правил внести контролируемые запрещённые зависимости в изолированный проверочный пример и убедиться, что соответствующее правило падает. Не добавлять фиктивные нарушения в рабочий код.

### 5.3. Проверки поведения

Статические архитектурные тесты не доказывают корректность конкурентности, подписок и остановки. Нужны отдельные проверки через интерфейсы:

- Первый подписчик включает сбор; второй использует тот же сбор; после отписки первого второй получает обновления; после последнего сбор прекращается.
- Независимые виды данных и TorrentId не отключают друг друга; повторная подписка получает текущее состояние.
- Гонка подписки/отписки не создаёт два исполнителя и не теряет действующего потребителя; отмена во время старта и завершения корректна.
- Медленный либо неисправный потребитель не блокирует остальных и не создаёт неограниченную очередь.
- Без UI и подписчиков передача, команды, восстановление и сохранение продолжаются.
- Скрытие главного окна в трей снимает подписки страниц и сохраняет подписку трея; возврат создаёт одну подписку активной страницы и показывает актуальные данные. Несколько циклов не накапливают обработчики или исполнителей.
- Потеря связи сохраняет последние значения с признаком недоступности; восстановление наблюдения снимает этот признак после актуальных данных. Возможность, не поддерживаемая движком, показана недоступной с объяснением.
- Разрешение зависимостей не создаёт движок и не выполняет I/O; остановка прекращает приём работы, завершает операции и сохраняет состояние.
- Общий набор проверок поведения адаптера применяется к каждой реально поддерживаемой реализации; второй адаптер не объявляется поддержанным по одному fake.

В CI архитектурные проверки и необходимые регрессии должны блокировать слияние при ошибке, если такой порядок принят владельцем и доступен в настройках репозитория. Не утверждать, что CI или защита ветки уже настроены.

## 6. Предлагаемый порядок перехода

1. Использовать подтверждённый объём раздела 2. Уточнить кандидатов будущих движков по исследованию; их внедрение не является условием первого этапа.
2. Сверить фактические зависимости и расположение состояния в коде; выбрать физические проекты и состав интерфейсов.
3. Добавить архитектурный контроль для согласованных правил. Временные исключения перечислить по точным зависимостям, причине и этапу удаления; глобально отключать правила нельзя.
4. Последовательно перенести Torrents, Desktop и Updates, оставив App местом сборки. После каждого этапа сохранять собираемое приложение и выполнять относящиеся к нему регрессии.
5. Реализовать согласованный механизм подписок и доказать его поведение; момент этого этапа относительно переноса определить по зависимостям.
6. Удалить заменённые пути и временные исключения, обновить карту текущего кода и результаты проверок.

Перенос не разрешает автоматически менять формат/место хранения, версии зависимостей, правила удаления, запуска и трея. Новые возможности и изменение пользовательского поведения требуют явного согласования.

| MM-04 | Потеря связи | Оставлять последние данные с отметкой «связь потеряна» и автоматически восстанавливать наблюдение. Политика повторов команд этим не меняется |

| MM-06 | Неподдерживаемые возможности | Показывать недоступными с объяснением |

Названия движков и внешнее управление коллекцией — вопросы будущего адаптера. Они не блокируют сохранение текущей реализации MonoTorrent в первом этапе, но ограничения переносимости интерфейса должны быть записаны до объявления поддержки другого движка.

Технические решения, которые предлагается доверить реализации после утверждения правил: библиотека архитектурных проверок, транспорт локальных уведомлений, точное число проектов и формат текущих снимков. Эти решения должны быть объяснены и проверены, а не превращаться в дополнительные продуктовые вопросы без необходимости.

## 8. Условия завершения перехода

Это предложенные критерии приёмки, подлежащие уточнению после ответов:

- Ответы MM-01–MM-06 учтены; неопределённый второй движок исключён из реализации первого этапа и не объявлен поддержанным.
- Структура и фактические зависимости соответствуют утверждённой карте; временные исключения закрыты.
- Архитектурные проверки анализируют все целевые проекты и выявляют контрольные запрещённые зависимости.
- Подписки проходят проверки включения/отключения, нескольких потребителей, конкурентности и завершения; история не вводится.
- При скрытии в трей страницы отписываются, трей получает необходимые данные; после возврата активная страница показывает актуальное состояние без накопления подписок. Выполнены согласованные правила частоты, потери связи и неподдерживаемых возможностей.
- Существующие сценарии добавления, ранних команд, восстановления, выбора файлов, обоих режимов удаления, настроек, трея и выхода сохраняются и проверены по затронутому объёму.
- Headless-ядро работает без Desktop. Изоляция окон проверяется в рамках согласованного объёма многооконности.
- Проверены сборки/публикации согласованных конфигураций; неподтверждённые AOT/MSIX/архитектуры процессора перечислены как ограничения, а не объявлены проверенными.
- Не появились новые неограниченные очереди, фоновые задачи без владельца и неосвобождаемые подписки; результаты проверок и актуальная карта сохранены в документации.
