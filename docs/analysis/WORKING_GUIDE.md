# Как продолжать работу с NiTorrent

Актуализировано 2026-11-27. Инструкции владельца и применимые AGENTS.md имеют приоритет. Исторический запрет менять код в сеансе анализа от 23 ноября не отменяет позднее разрешение реализовать первый этап модульного монолита.

## Начало сеанса

1. Прочитать [README](README.md), [карту кода](CURRENT_CODE.md), [отчёт реализации](MODULAR_MONOLITH_IMPLEMENTED_2026-11-27.md) и затрагиваемые требования.
2. Проверить `git status`/diff: текущий большой перенос может быть ещё не закоммичен. Не восстанавливать старые каталоги через reset/checkout/clean и не откатывать чужие изменения.
3. Уточнить цель нового запроса по контексту. Первый этап завершён; следующий этап не выбран. Не запускать автоматически новые движки, многооконность или переписывание хранения.
4. Выбрать релевантные установленные skills. Владелец отдельно просил `refactor` из code-refactoring-skill для понятного и безопасного разбиения кода; для C# нужен также csharp-refactoring, для проектирования — codebase-design.
5. Найти фактический сценарий в исходниках. Старые TorrentEntry/workflow-документы и исторические имена файлов не доказывают наличие типов в текущем дереве.

## Правила изменения

- Desktop работает через Contracts; живые модели коллекции и типы MonoTorrent наружу не передаются.
- App выбирает адаптер; Infrastructure не зависит от MonoTorrent-сборки. Новые реализации должны соблюдать интерфейс модуля и проходить архитектурные проверки.
- Сессия и передача независимы от UI-подписок. Отписка останавливает дополнительный сбор для отображения, а не скачивание/раздачу.
- Подписки принадлежат потребителям и освобождаются при уходе. Не заводить второй polling для трея или новую неограниченную очередь обновлений.
- Сохранить текущий путь/формат данных, смысл удаления, ранних команд и режимов закрытия, если задача не разрешает менять их.
- Не выбирать пользовательское поведение из старого плана при наличии нового согласованного ТЗ. Разногласия фиксировать в [вопросах](QUESTIONS.md), не объявляя реализацию подтверждённой по одному документу.

## Проверка

Команды managed x64 и матрица доказательств находятся в [отчёте реализации](MODULAR_MONOLITH_IMPLEMENTED_2026-11-27.md). Перед .NET-тестами применять run-tests; при изменении тестов — code-testing. Активные проекты находятся в `tests`, имена сборок сохранены.

Проверять затронутый сценарий, ошибки/отмену и соответствующие регрессии. Для удаления использовать только подготовленные файлы; для UI — отдельный NITORRENT_DATA_ROOT. Не использовать пользовательский профиль ради smoke-теста.

При отказе регистрации нативного значка в песочнице отделять ограничение среды от ошибки программы: тот же изолированный UI-сценарий вне песочницы ранее прошёл. Это не разрешение ослаблять тесты или менять правила трея.

В отчёте различать чтение кода, сборку, автоматический тест и реальный UI-сценарий. Предыдущий успешный прогон не подтверждает новую ревизию; managed-проверка не доказывает AOT/MSIX/ARM64. Публикация и отправка изменений не следуют из разрешения локальной реализации.

После работы обновить затронутые рабочие документы и ограничения. Исторические результаты сохранять с датой; текущее состояние не добавлять в старый отчёт как якобы результат того же прогона.
